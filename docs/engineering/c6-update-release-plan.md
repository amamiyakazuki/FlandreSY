# C6：更新与发布计划（C6a 全 A 已批准）

2026-10-17，审查基线 main `83869ae5200a6b6b4a97e5be3db70b7c5dc4797d`。用户先要求规划，随后选择“1A2A3A，开始”，批准 C6a 实施；沿用模块分支、测试后合入 main/推送、核对 CI 后停止，不创建 PR、不发布。C6b 正式候选构建/覆盖升级/发布未授权。

## 目标与证据

C6 主要处理 RA-09（更新入口不分平台、专用包覆盖升级受阻）和 DEBT-03（签名路径解析不一致），同时补齐同一更新/发布链路的结果校验。营销版本号如 `2.1.4` 用于用户识别；Android 内部版本码用于系统判断升级，前者变大不代表后者满足安装要求。

| 已确认问题 | 证据与影响 |
|---|---|
| 更新固定指向通用 APK | `lib/src/more/version_check.dart` 只读取 `downloads.github`；`about_dialog.dart` 不分平台直接打开。iOS 也会得到 Android 下载动作 |
| 包型版本码断层 | 2.1.4 发布记录为通用 6、ARM64 2006、x64 4006；本机 Flutter 插件确认分包使用基础版本码加 ABI 偏移。后续通用包若仍小幅递增，不能覆盖旧专用包 |
| 版本结果可能不可信 | `VersionInfo.fromJson` 将非字符串转字符串；仅检查非空，畸形版本仍通过数字兜底比较；本机版本读取失败回退过时常量 `2.1.1`。未使用安装包 buildNumber/packageName 区分构建与 Debug |
| 下载失败处理不完整 | 下载 URL 仅 tryParse，无 HTTPS/目标来源约束；launchUrl 返回 false 有提示，但抛出异常未兜底。打开浏览器成功不等于下载或安装成功 |
| 签名路径存在两种口径 | 脚本与 `key.properties.example` 相对 `android/`，Gradle 的 `file(...)` 相对 `android/app/`；绝对路径不受影响。不是已确认线上签名事故 |
| 正式产物校验依靠人工 | 脚本只确认签名配置非空/文件存在，随后打印产物与校验和；没有自动核对包名、版本码、证书、debuggable、ABI 与版本清单。直接 Gradle release 构建缺配置会回退 Debug 签名 |
| 候选版本与公开清单耦合 | 脚本要求 pubspec 与 main 上公开更新清单版本一致；提前合入候选清单可能让旧客户端在资产可下载前得到新链接。当前没有发现 2.1.4 链接失效 |

本轮只读核验 GitHub：最新正式 Release 为 [v2.1.4](https://github.com/amamiyakazuki/FlandreSY/releases/tag/v2.1.4)，存在通用、ARM64、x64 APK 和 AAB，无 iOS 分发资产；远端 main 清单仍指向该通用 APK。通用约 71 MB、专用约 42–45 MB，供方案取舍参考，不代表未来包大小。未下载并重新解析所有历史 APK，`4006` 只是现有发布记录中的已知最高码，不当作全历史已审计上限。

平台依据：Android 使用版本码防止降级，连续发布应递增；应用签名关系也是覆盖安装条件，不能靠改显示版本或让用户卸载解决。[Android 版本规则](https://developer.android.com/studio/publish/versioning)、[应用签名](https://developer.android.com/studio/publish/app-signing)。Flutter 的 build-name/build-number 对应 Android 的版本名/码，分包与通用包应分别核验实际输出。[Flutter 发布说明](https://docs.flutter.dev/deployment/android)。iOS TestFlight 需要独立的上传、分发与测试流程，当前无签名 CI 产物不能代替该渠道。[Apple TestFlight](https://developer.apple.com/testflight/)

## 决策记录

用户已选择 **1A＋2A＋3A**；B 方案仅保留比较背景，未实施。

| 决策 | A（推荐） | B | 代价与前置条件 |
|---|---|---|---|
| 1. Android 分发包型 | 以后 GitHub 面向用户只提供 ARM64+x64 通用 APK；保留旧 Release 及资产。首次新正式包的版本码须高于核验过的所有受支持旧包，此后统一递增 | 继续提供通用与各架构专用 APK，为新包统一版本码规则并补包型/架构选择；兼容旧客户端固定通用链接 | A 下载稍大，但旧专用包可迁到一个统一渠道；B 节省下载量，需定制并验证 Flutter 分包版本码规则和更多升级组合。两者都不能继续依赖“用户自己认出旧包型”作为唯一修复 |
| 2. iOS 更新入口 | 明确“暂未提供 iOS 更新渠道”，不显示 APK 下载或误报“已是最新”；可展示项目发布说明 | 接入已经可用的 TestFlight / App Store 更新入口，按 iOS 独立版本判断 | B 需用户提供真实渠道链接、版本及可用状态；若尚未建立渠道，签名/上传/审核属于另行确认的发布工作，不能编造地址 |
| 3. 发布方式 | 保留本地构建、人工发布；增加脚本自动校验和分阶段清单，正式发布仍由用户单独授权 | 新建 GitHub Actions 手动触发的正式签名/发布流程 | A 不迁移密钥、维护成本较低；B 需另定 GitHub 密钥托管、写权限和发布确认步骤。两者均不因普通推送自动发布 |

AAB 不作为应用内直接下载/安装入口；选 1A 时保留按需构建 AAB 的能力，但不默认向用户提供 AAB。32 位 Android、商店新渠道和第三方分发不在本次范围。上述 A/B 都不修改既有 applicationId 或签名身份。

## 建议分为两个验收阶段

### C6a：更新入口和发布工具修复

**1. 更新状态与平台分流**

- 统一读取真实安装版本、构建号和包名；元数据读取失败显示“无法确认当前版本”，不能拿 `2.1.1` 当真值。关于页与检查更新共用来源。
- 明确区分有更新、无可用更新、当前平台暂无渠道、版本未知、网络/清单错误。比线上版本新的本地构建不被诱导降级。
- Android 正式包比较显示版本及内部版本码；同显示版本的构建修订需要明确元数据才能判断。Debug 包作为独立安装，仅提供正式版信息，不宣称能覆盖 Debug。
- iOS 按所选方案处理，绝不使用顶层 Android APK 兜底。其他未支持平台明确暂无渠道。C5a 的 iOS 住理控制限制不因更新页改动而解除。
- 严格校验必需字段类型、版本语义与平台链接。缺字段、畸形版本不再降级成数字猜测；当前仓库 HTTPS Release 下载/说明地址为默认允许目标，iOS 正式渠道仅按选定配置开放。
- 下载失败/异常可重试；按钮防重复触发，离开页面后的迟到结果不更新已销毁界面。浏览器打开成功只表示已打开链接；长更新说明支持滚动和大字号。

**2. 兼容旧客户端的版本清单**

- 保持旧地址 `assets/public/version.json` 与旧字段 `version/release_date/changelog/downloads.github` 可读；旧字段继续表达已公开的 Android 稳定版。新客户端可使用新增的按平台字段、buildNumber 与渠道状态。
- 旧清单缺少安装兼容元数据时，新客户端最多提示查看 Release 说明，不承诺可以直接覆盖；现有 Android 顶层字段不能被 iOS 使用。
- 候选构建信息与公开稳定版清单分开：C6a 不把 2.1.4 清单改成尚未存在的下一版本，不决定下一正式版本号。
- `public/version.json` 当前无运行时代码引用，先保留为由同一源生成的兼容副本，增加一致性校验，避免未经确认删除旧路径。
- 后续发布按“候选构建→产物核验/安装验收→明确授权→上传并公开 Release→验证公开资产可访问→更新稳定清单”的顺序。单独上传草稿资产不算旧客户端可下载；中途失败保持旧稳定清单，不覆盖旧资产。

**3. 发布构建与签名校验**

- 相对 keystore 路径统一按已有示例的 `android/` 解析，绝对路径保持；支持含空格路径及标准 properties 格式。脚本与 Gradle 使用一致语义，不输出密码、私钥或不必要的签名路径。
- 正式发布路径缺少签名必须失败，不允许把 Debug 回退包当正式包；建议 release 构建要求正式配置，独立 Debug 仍无需密钥。本期不提供无正式密钥的 release 模式开关，普通本地验证使用独立 Debug。
- 构建前校验候选版本、历史版本码基线、支持的 ABI、工具链及锁定依赖。Gradle 的任务区分不能误伤正常 Debug CI。
- 构建后检查实际 APK 的 applicationId、versionName/versionCode、非 debuggable、ABI、证书摘要与受支持旧包一致；按需 AAB 单独检查，不能用 AAB 结果替代 APK。
- 输出此次构建的精确文件清单、大小、SHA-256、源码提交及工具链信息；不把目录中残留旧文件当新产物。校验工具缺失或任何项目不符合时失败，不静默跳过。校验和在 macOS/Linux 均能生成。
- 选 1A 时正式流程停止默认生成新专用 APK；迁移版本码需要先补齐受支持旧资产清单，不能机械设置为 `4007` 就宣称兼容全历史。

**建议实施顺序**：版本/链接失败用例与平台策略 → 更新入口和清单兼容 → 发布校验与签名路径 → 自动回归/静态分析/CI → docs/engineering 验收记录。模块分支 `codex/c6-update-release`；按已批准方式提交、合入 main、推送并核对 CI 后停止，不创建 PR、不发布。

### C6b：发布前产物与覆盖升级验收

这是 C6a 自动测试无法代替的部分，实际执行需用户另行确认候选版本及构建/设备范围；不等于立即发布。

1. 只读盘点拟支持的旧正式版本与三类 APK，记录真实包名、版本码、签名证书及 ABI；历史产物取不到时明确未验，不猜全历史上限。由用户确认要支持的升级起点，至少覆盖当前 2.1.4 三种包型，并检查 C1 前历史迁移路径。
2. 指定下一候选版本、严格更高的版本码和原有签名后，构建正式签名候选包，核验报告。更高版本码只是必要条件，不能代替安装测试。
3. ARM64/x64 对应设备或模拟器上分别验证旧通用/旧专用→新目标包；保留本地设备、账号配置、历史和活动记录。C1 升级后要求重新登录是既定行为，不误判为数据丢失；不触发设备控制或真实支付。
4. 失败不能建议卸载绕过；记录包名/证书/版本码/平台兼容原因。运行时问题回退可分发修复代码并使用更高版本码，不承诺直接安装旧低码包。
5. 用户确认验收与发布范围后才公开 Release 并更新在线稳定清单。iOS 若选 2B，另做已选渠道安装验证；无签名 CI 不记为正式分发完成。

## 验收矩阵

| 层次 | 必须覆盖 |
|---|---|
| 更新服务 | 版本高/低/相同、同版本更高构建、预发布语义、未知本机版本；HTTP 失败、超时、非对象/缺字段/错类型/坏链接；空/损坏清单不报最新 |
| 平台与页面 | Android 正式/Debug、iOS/未支持平台；旧格式与扩展格式；只展示当前平台动作；链接 false/异常、重复点击、销毁后返回；长说明/320 宽/2 倍文字 |
| 发布工具 | 相对/绝对/空格路径一致；缺签名失败但 Debug 可构建；版本不递增、证书不符、错误包名/ABI/debuggable/旧产物被阻止；稳定清单不提前改变 |
| 自动检查 | 专项、全量、analyze；脚本校验用临时假配置/固定产物元数据，不需要真实密钥；main 同提交 Android/iOS CI 单独记录 |
| 正式产物 | 真实签名 APK 元信息、证书与历史基线、校验和、源码对应关系；不是只看构建命令退出码 |
| 升级/发布 | 所选历史包型覆盖安装并保留数据；公开链接可访问且匹配资产；更新清单只能引用已公开版本；独立记录真机、服务与发布证据 |

## 边界与当前状态

不实现应用内静默安装、后台下载服务、自动发版、强制更新、iOS BLE C5b、D1/E1 或新商店上架；不更换签名、不卸载旧应用、不删除旧 Release。CI 版本差异 DEBT-04 保留为独立工程维护事项，本期只核验发布工具与锁定依赖，不顺手升级整套工具链。

C6a 已完成实现与本地验证，见 [验收记录](c6a-update-release-acceptance.md)。实际正式候选与历史覆盖升级仍待 C6b，不能把工具测试当作实体安装成功；在线稳定清单和 pubspec 保持 2.1.4 不变，未发布。
