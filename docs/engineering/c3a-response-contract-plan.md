# C3a：接口结果校验与异常时的数据保全

状态：用户已批准 A 方案及完整 C3a 实施、测试后合入 main 并推送 GitHub，确认 CI 后停止；不创建 PR、不发布。实施基线：main `86697a9670520addaf84de2cb924789dde99c49f`。结果见 [验收记录](c3a-response-contract-acceptance.md)。

## 为什么推荐先做

RA-13 是异常响应条件下的 P1 风险：U净和 798 的 JSON 传输层只拒绝“数值且非零”的 code，缺失、null 或字符串错误码可能被放行。洗衣取消随后可把本地订单写成已取消；798 开关操作也可能把没有成功证据的响应当成完成。代码路径已确认，尚未证明线上返回过这些异常格式。

C1 只为旧 U净订单核对增加了严格校验，普通业务仍保留旧规则。因此建议将 RA-13 从原 C3 / D1 拆成一个独立模块；模块编号表示范围，不要求按数字顺序实施。

| 候选 | 主要收益 | 推荐顺序及条件 |
|---|---|---|
| C3a 接口结果校验 | 阻止异常响应误报控制成功、误清活动记录 | 本轮首选；可用离线异常响应明确验证 |
| C2 本地设备一致性 | 修复刷新覆盖编辑、导入坏数据及刷新伪成功（RA-02/03/14） | C3a 后的首选候选，尚未批准 |
| C3b 洗衣状态与同步 | 解决启动中按钮无动作、活动单状态长期不更新（RA-04/05） | 与 C3a 分开，需确认状态和刷新频率 |
| C5 权限与 iOS BLE | 处理平台权限与设备身份匹配（RA-07/08） | 若当前重点是 iOS 实际开水，应优先确认该模块；构建成功不能替代设备验证 |

## 本模块做什么

1. **明确成功响应规则。** U净和 798 的 JSON 响应必须为对象，并有明确成功码。区分 HTTP 失败、业务拒绝和格式异常；格式异常不能被猜成账号失效。
2. **按端点区分数据要求。** “请求已被服务端接受”的确认接口与“返回账号/订单资料”的查询接口分别核对。不能一刀切要求所有成功响应都带非空 data；也不能用空对象替代必需业务数据后伪报成功。
3. **保留未确认结果。** 重点验证洗衣取消、启停及 798 开关：异常响应或后续查询失败时，不写伪终态、不清除原活动记录；提示结果未确认，不自动重发控制命令。账号检测遇到异常格式应是“无法验证”，不能是“正常”或无依据登出。
4. **保护 C1。** 旧记录核对仍必须具备明确成功、非空详情、订单及账号匹配证据；不放宽原有门禁，也不改变普通存储与安全凭据保全方式。

JSON 传输层收紧会共同影响两服务的登录、短信、查询、创建、支付参数及收藏调用；这些调用纳入兼容回归，但不扩展其业务功能。798 验证码图片接口不适用 JSON 成功码规则。

## 明确不做

- 不处理 C2 设备列表并发/导入，不接 798 实时设备状态、历史或删除收藏界面。
- 不处理洗衣启动中按钮（RA-04）、新增轮询或改变刷新频率（RA-05）。
- 不更改住理协议、BLE 设备匹配、权限、更新包、支付渠道或发布版本。
- 不新增订单状态机或数据库迁移；不重新设计超时重试、40 分钟恢复及热水控制规则。
- 不用真实账号下单、支付或开关设备验证；如实现发现必须扩展上述边界，停下记录并重新确认。

## 已确认的方案（全部采用 A）

| 决策 | 推荐方案 A | 可选方案 B |
|---|---|---|
| 成功码 | 仅接受 JSON 数值 0；缺失、null、布尔、字符串及非零均不视为成功 | 同时兼容字符串 "0"；仅这一精确值，不宽松转换其他内容 |
| 无数据的控制确认 | 对当前只需要成功确认的端点，允许明确 code=0 且没有 data；界面只表达接口确认，不能声称已物理停水 | 即使 code=0 也须额外查状态才算完成；需另行扩大只读核对范围，不能直接套用到本模块 |
| 未知结果 | 保留记录并明确“结果未确认”，不自动重发；继续保留已有手动核对/停止能力 | 扩展为自动只读核对与恢复流程；请求次数、可靠判据和状态变化另立计划 |

建议整体采用 A。它修复“没有成功证据也当成功”的漏洞，同时避免凭空要求服务端返回不存在的字段。现有仓库注释约定 code==0，但不等于所有真实服务端格式均已验证；若后续有可信响应证明字符串 "0" 必需，先记录兼容证据再调整。

## 实施步骤

1. **固定契约与复现。** 从当前请求和已有协议材料列出两服务的端点表：成功码、data 是否必需、失败后的记录与提示。用本地 HTTP 服务覆盖真实传输解析，先复现缺失 code 等误通过；每组同时有正常成功用例，避免测试环境固定 HTTP 400 造成假通过。
2. **收紧传输校验。** 在两个现有传输类中处理成功码和格式错误，保留已确认的 HTTP 401/403 行为；复核非零业务错误映射，不扩大为任意错误都清登录。保留 U净返回 data、798 返回外层对象的既有接口形状。
3. **检查调用后的行为。** 在受影响的 adapter / action 层修正必要的数据检查与提示，确保取消、启停及账号检测不会因格式异常提交成功；保留原 ID、owner、会话、凭据和已知状态。只改能由 RA-13 复现证明必要的路径。
4. **回归与记录。** 执行专项回归、静态分析、全量测试，检查 C1 门禁、认证代次、存储失败与控制去重未退化；按确切提交记录 Android / iOS CI 结果，真实服务项保持未验证。
5. **按获批交付范围收口。** 使用 `codex/c3a-response-contract` 模块分支、小步提交，不创建 PR。用户已授权测试后合入 main 并推送 GitHub，核验 CI。完成后停止，不发布，不自动进入 C2。

预计涉及：`io_ujing_transport.dart`、`io_shower798_transport.dart`、对应 transport 契约注释；必要时涉及 `ujing_http_adapter.dart`、`real_shower798_adapter.dart`、`washer_actions.dart`、`hotwater_actions.dart` 和账号检测反馈路径；新增专项测试及本目录验收记录。不提前承诺每个文件都必须修改。

## 实施采用的端点规则

所有 JSON 端点均须 HTTP 2xx、顶层对象及数值 code=0；下表数据字段来自当前调用所需信息，不新增服务端能力。非零业务错误保持错误消息，不猜测成鉴权失效；HTTP 401/403 保持现有鉴权拒绝行为。

| 服务 / 端点 | 成功后必要数据 / 行为 |
|---|---|
| U净 captcha | 仅确认，允许没有 data |
| U净 login | 非空字符串 token；缺失/类型错误不覆盖 adapter 旧 token |
| U净 home/scanCode | 有效 service 且为 water 才继续饮水流程 |
| U净 changeWithScan + currentInfo | 从 currentInfo 或已有 subject 余额字段取得有效数值；不能把缺失当零余额。账号检测单独要求 currentInfo 有有效余额 |
| U净 water/createWaterOrder、orders/create | 有效标量 orderId；不接收空值/零占位；先保留创建返回的 ID，再独立查询详情 |
| U净 water/waterOrderDetail、orders/{id}/detail | 有效 orderStatus / status；若返回 orderId 必须匹配请求。未知的非空状态保留原有非终态处理；C1 另要求非空详情与返回的账号、ID 证据 |
| U净 devices/scanWasherCode、program/info | 有效 deviceId、明确 createOrderEnabled；获取可下单套餐时须有 storeId。不可下单的正常响应保留 |
| U净 payment/arguments | payInfo.orderInfo 必须为非空字符串，错误类型不触发支付 launcher；付款后仍查订单 |
| U净 orders/{id}/control/start、control/stop、cancel | 仅确认允许没有 data；启停后仍按现有流程查详情，异常详情不提交成功；取消仅在明确确认后写终态 |
| 798 captcha 图片 | 保留二进制路径，不套用 JSON 成功码规则 |
| 798 acc/login/code、dev/favo、dev/start、dev/end | 仅确认允许没有 data；开关提示只称请求已确认，需用户核对设备；不自动重复控制 |
| 798 acc/login | data.al.token 必须为非空字符串 |
| 798 ui/app/master | data.account 非 null、favos 是列表且条目有有效 ID；空列表合法，坏列表不当空列表覆盖；缺字段不触发鉴权清理 |
| 798 ui/app/dev/status | 至少有能解析的 gene/sub 状态；缺失不伪报忙碌，未新增此接口的 UI 调用 |

没有改变存储 schema、订单轮询或 40 分钟恢复窗口。798 原有 uncertain 会话恢复时继续提示待确认；已确认请求不等同于物理水流证据。
