# C6b：候选版本与旧包覆盖升级验收计划

2026-10-17；基线 main `648032940f5779939428dda3f235ede606b5ff89`。**用户已批准 1A＋2A＋3A，并要求先检查现有环境，缺少设备或测试数据时停止，不发布。前置检查发现缺项后，用户确认暂无备用设备和测试数据并明确暂停；未构建、签名或安装。**见[前置检查与待验记录](c6b-candidate-upgrade-acceptance.md)。

## 目标与已确认边界

验证同一个正式签名候选 APK 能否覆盖选定旧包，并保留旧数据。C6a 的自动测试和 CI 只证明代码与工具检查通过，不能代替本阶段。

沿用已批准的 C6 策略，不重复决策：新包为 ARM64＋x86_64 通用 APK；保留旧 Release；iOS 暂无更新渠道；本地构建、单独授权后人工发布。本阶段不构建 AAB、不恢复产品模拟模式、不扩展 32 位支持、不做真实支付或设备控制，也不进入 C5b/D1/E1。

## 只读核对结果

- 当前源码版本为 `2.1.4+6`，远端稳定清单仍指向 2.1.4。
- [v2.1.4](https://github.com/amamiyakazuki/FlandreSY/releases/tag/v2.1.4)、[v2.1.3](https://github.com/amamiyakazuki/FlandreSY/releases/tag/v2.1.3)、[v2.1.2](https://github.com/amamiyakazuki/FlandreSY/releases/tag/v2.1.2) 均公开提供通用、ARM64、x86_64 三种 APK，以及本期不使用的 AAB；已读取 GitHub 资产名称、大小、SHA-256 元数据。
- 既有发布验收记录中的 2.1.4 内部版本码分别为 6、2006、4006；这是历史记录，本轮没有下载 APK 重新解析，不能据此宣称全历史最高码就是 4006。
- 更早版本仍有公开资产；2.0.0 还有 armeabi-v7a 包。它们的架构、签名与迁移路径未经本轮验证，不默认加入覆盖承诺。
- 当前工作区有尚未提交的本地审查记录。正式工具要求干净源码；后续应在隔离工作区准备候选提交，保留原工作区记录，不清理或重置用户文件。

## 已确认方案

以下编号仅属于 C6b，与已批准的 C6a 选项分开。用户已选择全部 A；B 仅保留比较背景。

| 决策 | A（推荐） | B |
|---|---|---|
| 1. 候选显示版本 | `2.2.0`：集中承载 C1～C6a 的维护与行为调整 | `2.1.5`：继续沿用补丁版本编号 |
| 2. 旧包验收范围 | 2.1.2、2.1.3、2.1.4 的三种 APK，共 9 个旧资产、12 条安装路径 | 仅 2.1.4 三种 APK，共 3 个旧资产、4 条安装路径；更早版本明确未验 |
| 3. 执行深度 | 完成正式候选检查及覆盖安装：ARM64 备用测试机＋可用的 x86_64 测试设备/模拟器，人工步骤与用户配合完成 | 先只完成正式候选和旧包元信息检查，安装与数据验收留待设备具备；C6b 保持未完成 |

方案 1 的内部构建号均暂建议 **5000**，最终须满足“高于所选全部旧 APK 的实际版本码及已公开构建号”。实际基线若不满足，停止并请用户重新选码。显示版本用于识别版本，内部版本码才参与 Android 升级判断，二者不能互相代替。[Android 版本规则](https://developer.android.com/studio/publish/versioning)

显示版本 `2.2.0` 已确认，内部码 `5000` 仍须实际旧包基线核验，目前未修改源码版本。“候选”表示尚在验收，不创建 `-rc` 标签或预发布 Release；现有正式构建工具使用 `x.y.z+构建号`。若验收后修复代码，使用更高构建号重新生成并核验，旧报告不得套用到新文件。

选择 3A 时还需确认：是否有可用于测试的 ARM64 备用 Android 设备、Android 版本，以及 x86_64 测试环境是否可用。不默认当前电脑能运行该架构模拟器；设备缺失时列为阻塞，不计通过。含真实在用数据的主力手机不作为第一轮测试环境。

## 安装与数据验收范围

对方案 2 所选的**每个旧版本**执行以下四条路径，新目标均为同一个通用候选 APK：

| 旧包 | 验收环境 | 要证明的结果 |
|---|---|---|
| 通用 APK | ARM64 | 覆盖安装，旧数据仍在 |
| ARM64 专用 APK | ARM64 | 跨包型覆盖安装，旧数据仍在 |
| 通用 APK | x86_64 | 覆盖安装，旧数据仍在 |
| x86_64 专用 APK | x86_64 | 跨包型覆盖安装，旧数据仍在 |

每条路径使用独立的可丢弃测试实例/快照：安装旧版、准备非敏感测试数据并记录，再直接覆盖到候选版。**覆盖步骤禁止卸载、清除数据、降级强装或更换签名绕过失败。**Android 版本和设备型号逐条记录；验收结论仅适用于实际测试环境，不推断所有系统版本均已通过。最低系统要求另从旧、新 APK 元信息比较。

所有路径检查本地设备与设置保留、首启可用、二次启动不重复破坏迁移、更新入口不会诱导回装线上旧版。最早与最新所选版本另做完整数据组，中间版本做基本保全检查；完整数据组在两种架构上各至少覆盖一次：

| 数据/场景 | 通过标准 |
|---|---|
| 全新安装 | 启动正常，无凭空出现的旧账号、设备、活动或迁移提示 |
| 本地设备与偏好 | 对比升级前后的条目、编辑字段、隐藏状态和设置；不能以“页面能打开”代替对账 |
| 旧登录状态 | 各服务按 C1 要求重新登录；普通配置和业务记录仍保留，不把重新登录误报为数据丢失；旧凭据不得继续授权控制 |
| 来源不明/旧模拟活动 | 原记录保留并待核对，不能自动删除、视为已结束或用于控制；旧开关为 false/缺失也不能证明数据真实 |
| 历史与账号归属 | 已有归属不串号；无归属档案继续保留，不擅自分给当前账号；重新登录本身不等于活动核验通过 |
| 离线首启、退出再启动 | 网络失败不清空本地数据，迁移状态可恢复；再次启动不重复丢记录或恢复旧授权 |
| 备份与失败保护 | 普通偏好备份不包含安全存储中的凭据；保全失败不得继续破坏原数据。实际失败注入无法安全完成时，单列自动测试证据及真机未验项 |

数据准备优先使用旧版 UI 可建立的非敏感本地数据和现有隔离测试资料。正式 APK 不假定可用调试接口直接写入私有存储；不能构造的活动、凭据和多账号场景列为待补证据，不用空数据测试冒充通过。若必须使用真实测试账号或访问业务服务，先列出具体操作与数据范围交用户决定，不触发支付、启动、停止等控制。自动化迁移夹具作为补充证据，与真实 APK 升级结果分别记录。

## 实施顺序

**环境门槛（用户新增约束）**：先检查现有工具、连接设备、已配置模拟器与可用于正式旧包的测试资料。缺少设备或测试数据即停止告知，不继续下载基线、准备候选或构建。2026-10-17 已在此处停止，以下步骤尚未执行。

1. **固定旧包基线**：下载选定公开 APK，按 GitHub 可信摘要校验，逐个读取包名、版本名/码、ABI、最低系统要求、debuggable 与证书摘要，形成仓库外基线文件。签名不一致、资产缺失或版本码超出提案时停止，不悄悄缩减范围。
2. **准备候选源码**：隔离工作区和模块分支 `codex/c6b-candidate-upgrade`，仅调整已选候选版本及验收所需文档；保留稳定清单为 2.1.4，锁定依赖。记录精确提交。需要源码或工具修复时先记录问题、确认属于 C6b；涉及其他模块立即停下请示。
3. **构建与产物核验**：预检、静态分析、全量 Flutter 测试、发布工具回归；使用原正式签名生成通用 APK，核验实际版本、包名、证书、架构、非调试标志、文件大小与 SHA-256。凭据不进入日志或 Git。签名关系必须符合覆盖安装要求。[Android 应用签名](https://developer.android.com/studio/publish/app-signing)
4. **按所选深度执行安装验收**：逐条记录安装结果、设备/系统、升级前后数据对账与首启/重启结果；失败保留日志及测试实例，不用卸载“修好”。产物若变化，重做受影响检查及安装路径。
5. **交付验收记录并停止**：公开的精简记录放 `docs/engineering/c6b-candidate-upgrade-acceptance.md`，原始报告、APK、测试账号资料留在本地；记录实际候选提交和 APK 摘要。沿用模块分支、无 PR 的方式；本轮不提交/推送，后续执行授权时明确是否包括测试通过后合入 main、推送及 CI 核验。无论采用哪种 Git 交付，均不自动发布。

## 完成标准与停止条件

- 产物通过：所选历史基线全部核验、新 APK 正式签名身份一致且版本码严格更高，工具报告与候选提交对应。
- 升级通过：所选安装路径完成，数据对账通过；未具备资料的完整数据场景逐项明确，不写“全部数据保全已验证”。只有关键安装和保全项齐全，才能将 C6b 标为完成；选择 3B 只能完成产物部分。
- 测试报告分开写自动检查、产物核验、设备安装、数据迁移、未验业务。C6a 的 522 项测试及既有 CI 不作为本次候选的新证据。
- 安装失败、数据减少、账号串用、来源不明活动恢复控制能力、签名/版本/架构异常，均阻止验收通过。修复方案涉及业务取舍时交用户选择；不自动降级回装旧包。
- **本阶段结束于“候选可评审”，不等于发布。**不建 Release（包括草稿/预发布）、不上传资产、不推送发布标签、不更新两个稳定版清单，也不执行发布后的清单生成工具。未来获准发布时使用通过验收的同一 APK 文件；重新构建需重新核验。

当前结论：方案已获批准，但用户因缺少设备和测试资料明确暂停 C6b；未经用户恢复不继续，C6b 尚未完成。RA-09 保持“C6a 已修复代码，C6b 覆盖升级待验”。
