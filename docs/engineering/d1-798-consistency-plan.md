## A 方案的具体边界

- **状态**：修改默认值与旧缓存展示规则，保留旧数据；没有本次可信查询证据就不显示实时空闲/忙碌。业务操作产生的“请求已确认”仍只表示请求结果，不能改成设备已停止等断言。不得改变开始/停止判断、订单恢复或自动重试规则。
- **登录**：校验失败、业务拒绝、网络错误、响应异常、列表加载失败、持久化失败分别反馈。清理与错误展示分开；清理失败自身也需可见且不重新开放控制。保留 C1 门禁、旧活动与历史保全，禁止新 token 与旧账号混用。刷新列表的普通错误继续保留登录，不借此扩大清理范围。
- **列表**：所有可写入口纳入同一顺序；切号、退出、鉴权失效和销毁使旧任务失效。不能只禁用按钮而忽略运行时并发调用。正在执行的服务器请求不假称已取消，迟到结果不得写入新账号。
- **保存**：本地选择/刷新成功落盘后再发布已保存状态；失败保留上一份已确认列表及可重试输入。添加服务器已确认但后续刷新/保存失败，提示“添加请求已确认，列表尚未同步/保存”，后续只重试读取与保存，不自动重发添加。
- **选择**：刷新后当前 ID 仍存在则保留；已不在已确认新列表中则清空当前选择并提示重选，不擅自选择另一个设备。活动会话仍引用原设备并继续保全，不随着列表选择清理。
- **页面**：分别呈现登录与列表操作反馈，避免刷新把登录错误冲掉；添加失败保留设备号，重复操作有反馈。仅调整现有页面必要文案与忙碌状态，不做视觉重设计。

不接通删除收藏、账号历史（GAP-02），不扩展短信业务、支付、设备控制、协议字段猜测或其他服务登录策略；若需要触及共享账号/存储逻辑，只做支持本模块的最小改动并验证其他服务原行为。发现必须改变其他模块契约时停止请示。
