- README 只保留面向使用者的功能介绍、迭代/修复、现有下载入口及使用说明；开发、CI 与发布流程移到 `docs/development.md`。未发布时仍标当前稳定版 2.1.4，不提供虚构的 2.2.0 下载链接。
- 准备 `docs/releases/2.2.0.md` **本地说明草稿**，只写用户可感知的功能迭代和修复，不放测试数、提交、CI 或开发流程。验收状态留在工程记录，不新增通过结论。
- 修正 `tools/release/README.md` 的操作衔接和 `SECURITY.md` 排版/诊断说明；历史 2.1.3/2.1.4 发布记录保留，不将旧建议改写成当时不存在的新承诺。不修改调试采集脚本。
- 检查 README 引用、图片路径、版本术语及文档之间一致性；不得把组件渲染图称为真机截图。核对 UI 变更后的全量测试、静态分析、发布工具回归。
- 清理确认可再生成的测试缓存、Python 字节码和系统目录元数据；保留测试源、基准图、验收截图、正式包、签名与个人资料。
- 本地模块分支提交确认范围后停止；不合入 main、不推送，不触发或宣称本提交 CI 通过。**不改 pubspec、不动稳定清单，不生成正式包。**

交付：可审阅的 README、Release 说明草稿、已入 Git 的外观修复和验收记录。阶段 1 完成不表示 C6b 已完成。

### 2. 环境和旧包基线

先落实下文资料；缺设备或数据即停止候选工作，不越过旧 C6b 的环境门槛。

条件具备并获执行确认后：核对两架构环境与测试资料；从原 Release 下载 9 个旧 APK，对照公开 SHA-256，读取实际包名、版本码、ABI、最低系统要求、签名、debuggable。确认候选构建号大于所选旧包及已公开构建号；若 5000 不满足、签名不符或文件缺失，列出证据和可行方案，交用户决定，不猜测或删减范围。

旧 APK 和原始报告放仓库外，公开文档只写必要摘要。阶段 2 完成不表示覆盖安装通过。

### 3. 正式候选构建与覆盖验收

固定包含阶段 1 结果的候选提交，在干净隔离工作区更新候选版本，使用原正式签名及锁定依赖构建。运行静态分析、全量 Flutter 测试、发布工具回归；核验实际包名、版本、签名、两种 ABI、非调试标志、SHA-256 与源码提交。此时稳定清单仍保持旧正式版。

每个旧版本执行以下四条路径，合计 12 条：

| 测试环境 | 旧包 → 同一个新通用 APK |
|---|---|
| ARM64 | 旧通用包 → 新通用包；旧 ARM64 专用包 → 新通用包 |
| x86_64 | 旧通用包 → 新通用包；旧 x86_64 专用包 → 新通用包 |

每条路径记录安装结果、设备/系统、升级前后设备列表与设置对账、首启与二次启动。最早/最新版本另做两架构完整数据组：旧登录失效后的重登、来源不明活动保全、历史归属隔离、离线首启、迁移失败保护；详见既有 [C6b 数据矩阵](c6b-candidate-upgrade-plan.md)。还要单列新装检查及更新入口检查。

升级步骤不卸载、不清数据、不降级强装。不同旧版基线需要独立可丢弃实例或快照；如需在备用机上重建下一组基线，先明确并确认该测试实例可清理，不能碰在用数据。正式 APK 不假定支持直接注入私有数据；无法准备或安全复现的场景保留未验。测试不触发支付或开关设备。

失败即保留证据并修复后复验；候选代码或 APK 变化则重新核验，不能套用旧摘要/报告。自动测试、产物校验、实际安装、数据迁移分别记结果，不把任何一层代替另一层。

### 4. 发布材料定稿并交用户确认

完成适用验收后，准备一份发布确认单：候选提交、版本/构建号、确切 APK 名称/大小/SHA-256、12 条路径结果、数据对账、CI 链接、未验与已知限制、最终 Release 正文和 README 发布切换差异。

提交/合入候选及文档按确认的 Git 方式执行；版本标签指向已验候选源码提交，APK 必须对应该提交。说明草稿和校验和准备好，**停在确认单，不创建远端标签或 Release，不上传、不更新在线清单**。

缺少关键覆盖或保全证据时，确认单只能标“待验”，不能建议按已验稳定版发布。若用户要调整支持范围，先另列方案，不擅自把原 C6b 改为完成。

### 5. 单独获准后发布

仅在用户明确批准确切候选及发布范围后：

1. 推送对应标签，上传并公开 GitHub Release，使用阶段 3 验收过的**同一个 APK 文件**，附校验和与发布说明。
2. 核对公开下载、文件大小及重新下载的 SHA-256，使用现有稳定清单工具生成待审文件。
3. 确认公开资产匹配后，同步两份 version.json 的兼容字段/平台元数据，更新 README 稳定版入口，提交推送并核对 CI、远端清单与下载指向。
4. 写实际发布时间、链接、提交和产物摘要；停止，不追加模块。

上传或核验失败时，保持旧稳定清单；若新 Release 已公开但后续步骤失败，准确记录部分发布状态并停止处理，不宣称整体成功。发布后若出现缺陷，先停止继续更新清单并报告；通常用更高构建号修复，不承诺旧低码包可直接降级覆盖，不自动删除旧版本。
