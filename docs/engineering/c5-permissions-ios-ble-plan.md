## 目标与证据

C5 对应 RA-07（权限流程不一致，P2）和 RA-08（iOS 目标识别不兼容，条件性 P1）。两者不能混为一谈：获得蓝牙授权，不代表已经能认出并控制正确的热水设备。

| 现状 | 证据 | 影响 |
|---|---|---|
| 首次引导请求相机、bluetoothScan、通知；更多页另请求 scan、connect、定位 | `lib/src/data/permission_service.dart`、`lib/src/more/permission_check.dart` | 同一设备的两处检测口径不同；更多页的“检测”实际上会申请权限 |
| iOS 也请求 Android 的 scan/connect，并启用定位但缺少用途描述 | `ios/Podfile`、`ios/Runner/Info.plist`；锁定 Apple 插件 9.6.1 的 PermissionManager / UnknownPermissionStrategy / LocationPermissionStrategy | scan/connect 落入未知策略；定位请求可能返回 MISSING_USAGE_DESCRIPTION，不应笼统当作用户拒绝 |
| 通知有引导承诺，但没有系统通知发送链路；当前 CocoaPods 配置未启用通知宏 | 同上及 lib/Android/iOS 通知调用检索 | 申请权限无法兑现状态提醒；是否移除申请及承诺需用户选择，关联既有 GAP-01，不新增提醒功能 |
| 更多页忽略打开设置的 bool 返回值；空结果集合被 every 判断为成功 | `lib/src/more/permission_check.dart:28` | 可能误报“已打开设置”或“权限已授予”；纳入 RA-07 的结果可信度修复 |
| 服务端 ble_mac 非空时直接与 remoteId 比较 | `lib/src/data/adapters/ble_target.dart`；`flutter_blue_plus_ble_transport.dart:119` | iOS remoteId 来自 CBPeripheral.identifier UUID，不能直接与硬件 MAC 相等 |
| 当前只使用名字和 remoteId，未解析广播身份；仅有 MAC/名称选择测试 | `real_zhuli_adapter.dart:148`、`test/ble_target_test.dart` | 不能凭现有代码证明广播包含 MAC、名称唯一，或握手已验证目标设备身份 |

平台依据：Android 12+ 使用扫描/连接授权，旧版扫描需要定位；当前 neverForLocation 可能过滤部分信标，需真机验证，不因猜测额外申请定位。[Android 官方权限说明](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)

Apple 将外设标识定义为 UUID；锁定 flutter_blue_plus 1.36.8 / Darwin 7.0.3 的代码也使用此值。**UUID 不是可直接转回服务端 MAC 的另一种写法**。[Apple identifier](https://developer.apple.com/documentation/corebluetooth/cbpeer/identifier)、[FlutterBluePlus 1.36.8](https://pub.dev/packages/flutter_blue_plus/versions/1.36.8)

权限以锁定版本 `permission_handler 12.0.3 / apple 9.6.1 / android 13.0.1` 为准。网上文档同时介绍 SPM 与 CocoaPods，通知默认设置不可跨安装方式照搬；本项目为 CocoaPods，已核对本机锁定源码的 `PERMISSION_NOTIFICATIONS` 默认值为 0。[插件版本说明](https://pub.dev/packages/permission_handler/versions/12.0.3)

## 已批准范围

### C5a：统一权限与明确能力边界

1. 首次引导、更多页、扫码入口与热水 BLE 入口共用一份按平台/系统版本制定的权限策略。保留“首次说明只出现一次”，但说明已读不等于系统已授权。
2. 分开“检查”和“申请”；拒绝、永久拒绝、受系统限制、暂时未知、读取失败、不适用分别反馈。蓝牙开关/硬件支持属于设备状态，不冒充权限状态；未知或缺失结果不算成功。
3. 返回前台/系统设置后重读状态；合并重复申请，避免插件与页面并发弹窗。扫码仍复用 mobile_scanner，BLE 仍复用 FlutterBluePlus，不更换插件或整套协议。
4. 打开系统设置由用户点击，回报真实打开结果。平台调用异常恢复成可重试提示，不让页面停在加载中；权限失败不触发开水、创建消费订单或发送控制指令。
5. 同步 AndroidManifest、Info.plist、Podfile 的实际权限清单与用途说明。按选定通知方案更新 `openspec/specs/real-permissions/spec.md`；不因蓝牙误请求给 iOS 补无业务用途的定位权限。
6. 按已选择的 1A：明确标识当前 iOS 住理 BLE 控制暂不可用，在进入真实扫描/控制流程前拦截；提示设备识别尚未适配，不伪报成权限拒绝或扫描超时。Android 保持既有目标选择规则；住理登录、历史、798/U净网络功能不受此限制。
7. iOS 已保存活动会话继续保留，不自动清除、不显示关水成功；不能通过关闭界面或撤销权限推断实体设备停止。本地清理仍沿用既有确认流程。

已实施权限矩阵（按受支持系统版本，不提高最低版本）：

| 平台 | 扫码 | 前台住理 BLE | 通知 |
|---|---|---|---|
| Android ≤30 | camera | locationWhenInUse 用于扫描；定位服务另查，旧蓝牙权限保留清单声明 | 不申请 |
| Android 31–32 | camera | bluetoothScan + bluetoothConnect，不额外申请定位 | 不申请 |
| Android 33+ | camera | bluetoothScan + bluetoothConnect | 不申请 |
| iOS 13+ | camera | C5a 明确不可用，不检查或申请蓝牙、scan/connect、定位 | 不申请 |

Android SDK 版本来自 `Build.VERSION.SDK_INT` 平台通道，读取失败明确提示错误，不猜测权限集合。蓝牙支持/开关仍由真实传输层分别检查。锁定插件在 iOS 13.0 的静态蓝牙查询限制不影响本期：C5a 将其视为未开放的能力，不调用蓝牙权限接口，也不把它伪报为拒绝；完整适配时须在 C5b 处理 13.0/13.1+ 差异。当前最低系统版本和依赖版本均不调整。

### C5b：取得身份依据后实现 iOS 设备识别

这部分有外部前置条件，不能靠单元测试或 CI 证明已可用：

- 至少一台可测试 iPhone 和真实住理设备，并能区分附近两台同名/同型号设备；Android 可作对照。
- 可核对的设备接口字段、广播样本及厂商/服务端协议依据。样本只保留需要的设备身份字段，不收集登录 token、secret、isn、支付串或无关用户数据。
- 必须明确什么字段将“扫码得到的设备 ID”与“iOS 扫描到的外设”关联，以及冲突、缺失、设备更换时如何处理。

候选身份来源是**调查方向，不是已经可用的方案**：广播 manufacturer/service data 中的设备身份（需明确编码、字节序与真实样本），或厂商提供的设备标识读取/身份核验协议。单纯看到 ff12 服务只证明协议类型，名称/RSSI 也不证明唯一身份；现有握手返回 isn 不足以证明身份校验契约成立。若需要连接后读身份，须先确认读取无控制副作用，核验成功之前禁止费率、开水和关水指令。

验证过身份后，iOS UUID 可作本机连接线索，不能直接充当跨手机永久身份；须设计失效、重新扫描和重新核验。开水和关水共用同一验证规则，不能只适配开启路径。无法唯一确认目标时结束本次操作并说明原因，不选择“第一个同名”或“信号最强”设备。

## 批准后的实施顺序与验收

1. 固定所选范围，补平台权限矩阵与错误反馈复现；引入可注入的平台版本/权限查询接口，避免测试触发真实系统弹窗。版本来源使用可靠平台接口，不猜系统字符串；不以本模块名义升级依赖。
2. 统一检查、申请、设置返回及生命周期刷新，按选择调整首次说明/通知范围和原生配置。
3. 按 1A 增加详情/权限页说明、运行时门禁、适配器和传输层门禁；保留旧会话及待核对标记。
4. 本地专项、全量测试和静态分析；记录构建/真机各自证据。CI 不替代设备识别验收。
5. 按本轮明确授权，以 `codex/c5a-permissions` 模块分支实现；测试通过后合入 main 并推送 GitHub，确认 main 同提交 Android/iOS CI 后停止，不创建 PR、不发布。
