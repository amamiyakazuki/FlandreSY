## Context

> 2026-09-19 M1-B 更新：本文下方保留原实现设计作为历史。用户已替换热水交互与恢复策略：开/关按钮始终可点，指令串行；缺本地关水信息时刷新订单；启动/前台恢复超过 40 分钟回待开水，否则保留已开水。不再使用订单基线判定、10 秒状态轮询或一小时补查。当前有效行为以同目录更新后的 hotwater-status-reconciliation 规格为准，Android 构建部分不变。

当前热水运行时在蓝牙控制开始前就写入进行中 session，随后把扫描、连接、握手、订单创建和启动确认阶段的异常统一视为“结果待确认”。应用重启时无法知道这个 session 是否真的向设备发送过启动指令，于是会恢复它并持续执行只读订单轮询；设备不在范围内时，这条路径会留下没有 `isn`、也无法停止或清除的异常状态。

工作区已有一组未完成的分阶段改动，但目前存在 Dart 编译错误、缺失的清理方法、旧 session 迁移后没有本地解除入口等问题。Android 方面，普通 `flutter build apk --release` 需要先恢复 Dart 编译健康；发布脚本还读取了过时的 `public/version.json`，而项目实际使用 `assets/public/version.json`，并且正式发布仍需要独立的签名配置。

约束：轮询必须是只读操作，不能用开/关水接口探测；真实住理协议和 BLE 合约不在本变更中重写；进程被系统终止期间不能执行 Dart 轮询，只能在下次启动或回到前台时补查。

## Goals / Non-Goals

**Goals:**

- 建立可持久化、可迁移的热水启动阶段模型，区分确定未发送、正在准备、结果不确定和已确认运行。
- 对扫描/连接/握手/订单创建等发送前失败自动清理本地 session，使用户可以立即重试。
- 对已经尝试发送设备指令但没有收到确认的情况保留 `uncertain`，重启和前台恢复时继续只读核对。
- 为旧版或缺少关水凭据的 session 提供明确的本地解除操作，并保证该操作不冒充设备已关闭。
- 保留账号、系统、设备和订单绑定，阻止过期异步结果覆盖新会话。
- 用单元、运行时和 widget 测试覆盖状态转换、持久化迁移、轮询失败、停止和本地解除。
- 使当前代码通过 `flutter analyze` 与 release APK 的 Dart 编译阶段，并修正发布脚本的版本清单前置校验。

**Non-Goals:**

- 不新增或猜测住理服务端的实时消费状态接口。
- 不在后台进程中维持蓝牙连接或订单轮询。
- 不因本地解除而调用停止设备接口，也不把本地清除描述为设备已经停止。
- 不修改三套账号登录协议、BLE 数据帧协议、支付流程或视觉主题。
- 不生成、提交或替用户填写正式 Android keystore；正式签名仍由发布环境提供。

## Decisions

### 1. 使用显式 session 状态机，并把写指令尝试作为持久化边界

会话阶段采用 `preparing → starting → active`，以及从启动指令尝试开始进入 `uncertain` 的分支。创建基线、扫描、连接、握手和订单创建阶段失败时，session 仍可被安全丢弃；拿到 `isn` 和启动订单后，在调用 BLE 写入前先持久化“已经进入不确定边界”的状态，写入或确认响应的任何异常都保留 `uncertain`。只有收到完整启动确认才转为 `active`。

这样可以覆盖“写入调用返回错误但设备可能已经收到部分数据”的情况，避免把 callback 在写入之后触发当作唯一事实。轮询只对 `active`/`uncertain` 开启。

备选方案是继续用一个布尔 `running` 或在所有异常后统一保留 session；前者无法表达风险边界，后者正是当前卡死问题的来源，因此不采用。

### 2. 旧 session 采用保守迁移，不自动推断设备状态

读取 v1 session 时映射为 `uncertain`，保留原账号、系统、设备、启动时间和基线；缺失的阶段、订单号或 `isn` 不补造。迁移后的首屏状态明确显示待确认，并提供本地解除入口，而不是自动删除可能仍在设备上运行的会话。

备选方案是启动时直接删除所有 v1 session；它能快速消除卡住界面，但可能让真实仍在供水的设备失去 App 控制上下文，因此不采用。

### 3. 清理分为“确定失败回滚”和“用户确认的本地解除”

运行时提供统一的 session 清理路径：确定的发送前失败自动清除普通设置中的 session、secure storage 中的 `isn` 和相关计时器；不确定状态由用户在热水详情页确认后执行相同的本地清除。清除操作不访问设备、不写服务端、不显示“已关闭”。成功关水则沿用现有停止流程，在设备确认成功后清理 session。

备选方案是把“本地解除”复用停止按钮；缺少 `isn` 时该按钮必然失败，而且语义会误导用户，所以不采用。

### 4. 进度回调只传输阶段事实，runtime 负责持久化和 UI

适配器继续负责真实 HTTP/BLE 编排，只通过结构化进度通知报告握手拿到 `isn`、订单创建完成和启动指令边界。Fake 适配器提供同样的阶段序列。runtime 在每个阶段检查 session ID、账号代次和销毁状态，过期回调直接丢弃。

备选方案是让 adapter 直接写入 runtime 或设置仓库；这会破坏适配器与状态层的边界，难以测试真实和 Fake 两条路径，因此不采用。

### 5. 发布校验以项目实际资源为唯一版本来源，并区分本地验证和正式发布

发布脚本读取 `assets/public/version.json`，将其中 marketing version 与 `pubspec.yaml` 的版本核对；版本不一致时在构建前失败并给出两个文件路径。正式发布脚本继续要求完整 `android/key.properties` 和存在的 keystore；普通 Flutter 本地 release 构建可沿用 debug fallback，但输出只能用于安装验证，不能宣称为正式分发包。

备选方案是继续读取根目录 `public/version.json` 或在脚本里复制一份版本数据；这会让内置清单、远程清单和构建校验出现漂移，因此不采用。

## Risks / Trade-offs

- **[Risk]** 启动指令已经发送但服务端订单历史生成较慢，`uncertain` 可能持续一段时间。 → **Mitigation:** 只读轮询、保留一小时补查策略和明确的待确认文案；不按本地时间强制结束。
- **[Risk]** 旧 v1 session 无法证明是否已发送设备指令。 → **Mitigation:** 保守恢复为 `uncertain`，提供二次确认的本地解除，不自动宣称停止。
- **[Risk]** 写入边界前后处理不一致会重新引入“确定失败误删”或“所有失败永久保留”。 → **Mitigation:** 在写入调用前持久化不确定阶段，并用 Fake adapter 测试每个边界。
- **[Risk]** secure storage 清理失败可能造成残留 `isn`。 → **Mitigation:** 清理路径记录失败并保留可重试的 session 清理状态；测试覆盖异常 repository。
- **[Risk]** release 构建受本机内存和签名环境影响。 → **Mitigation:** 先执行 analyze/test，再单独记录 Dart 编译、Gradle、签名三个阶段；发布脚本在构建前明确报告缺失配置。
- **[Risk]** 新 session 格式可能被旧版本二进制拒绝。 → **Mitigation:** 新版本继续完整读取 v1；上线前不做破坏性清理，回滚时保留本地验证包与 session 清理说明，必要时先恢复兼容读取再回滚。

## Migration Plan

1. 先修复当前工作区的编译错误，并补齐 session 状态模型、统一清理路径和 UI 本地解除入口。
2. 让新版本读取 v1 session 并以 `uncertain` 展示；新建或更新的 session 使用带阶段字段的版本格式。迁移不主动调用设备控制接口。
3. 通过 Fake/运行时回归测试后执行 `flutter analyze`、`flutter test` 和 `flutter build apk --release`；发布脚本另执行版本和签名前置校验。
4. 发布后首次恢复旧 session 时，用户可选择继续只读核对、尝试正常关水或确认清除本地记录。所有选择都不把本地清除描述成设备已停止。

回滚策略：代码回滚不会删除普通设置或 secure storage；v1 数据仍可被新版本读取。若已经写入新格式的 session，回滚到不认识该格式的旧二进制前，应先完成会话核对或本地清除，避免旧版本把未知数据误当成无 session。

## Open Questions

- 真实住理服务端生成消费记录的延迟和终态字段仍需真机验证；本变更只保证在证据不足时保持待确认，不把未知字段当作结束。
- 正式发布所需的 keystore 由发布者提供，本变更只修正校验和错误提示，不决定密钥存放或 CI secret 管理方式。
