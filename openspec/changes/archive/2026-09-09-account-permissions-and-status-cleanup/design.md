## Context

当前 Flutter 应用由 `ShuiShell`、`FakeShuiRuntime`、按服务拆分的 adapter，以及 shared preferences/secure storage 组成。权限引导只记录本地确认；账号中心在选择系统时提前修改首页偏好；热水轮询已有生命周期但真实状态字段仍不完整；多个文件保留历史 `GAL REVIEW REQUIRED` 注释。

## Goals / Non-Goals

**Goals:**

- 建立统一权限服务，真实查询并请求相机、蓝牙、通知权限，支持拒绝状态和生命周期恢复。
- 将默认洗浴系统的变更绑定到登录成功或账号页的明确勾选。
- 住理热水通过持久化会话和订单基线核对状态，798 保留现有空闲查询；证据不足保留待确认。
- 删除无效引导文案和历史门禁注释，保持现有 adapter 协议与接水轮询不变。

**Non-Goals:**

- 不重写三套账号的登录协议、验证码流程或 secure storage key。
- 不把历史订单强行解释为实时设备状态。
- 不在本变更中重做全局动效、视觉主题或 golden 测试。

## Decisions

1. **权限采用统一服务抽象。** 使用平台兼容的权限依赖或现有插件能力封装 `check/request`，由 Shell 在首次引导和回到前台时调用；各功能页仍保留失败后的局部错误提示。相比在扫码、蓝牙、通知模块分别请求，这能统一处理拒绝与永久拒绝。
2. **权限请求按能力分组而非无条件全量请求。** 首次引导请求当前产品确实需要的相机、蓝牙和通知权限；未使用的能力不触发弹窗。永久拒绝时提供打开系统设置的动作。
3. **默认系统在登录成功后写入。** 账号中心只导航到详情页。详情页登录成功后默认勾选对应系统；用户取消后不再自动写回。U净登录不改变洗浴偏好。相比进入详情即切换，这避免未登录系统污染首页行为。
4. **热水采用持久化会话和订单基线。** 住理启动前读取同设备订单基线，持久化账号、设备、系统、启动时间、已知订单；启动成功继续保存进行中状态。重启恢复为待确认并立即补查，前台每 10 秒查询，一小时主动补查；新消费记录推定本次结束，列表重排、旧订单消失、其他设备变化、失败均不结束。没有订单 ID 或可解析时间时不猜测。798 保持原空闲查询协议，但同样固定会话所属账号及设备。关水所需 isn 放 secure storage，不写入普通设置。未结束会话禁止重复启动。登录账号不匹配时保留会话且不查询错误账号。
5. **轮询与生命周期复用现有 runtime。** 继续使用固定 10 秒间隔、互斥请求、会话代次校验、前后台暂停和销毁停止；新增来源只扩展 adapter contract，不改变接水 5 秒轮询。

## Risks / Trade-offs

- [权限插件与平台版本差异] → 锁定兼容版本并补 Android/iOS 声明及真机验证矩阵。
- [服务端没有可用实时热水接口] → 明确展示未知状态，订单只作辅助证据，避免误报停止。
- [登录成功回调路径分散] → 在 runtime 的服务登录成功出口集中触发默认系统写入，并增加三套账号流程测试。
- [批量注释清理误删有效说明] → 仅匹配精确历史标记和其紧邻的 review 指引，不修改业务注释。

## Migration Plan

1. 先加入权限服务和平台配置，保留旧持久化字段以兼容已有安装。
2. 再调整账号详情成功回调和首页状态模型。
3. 接入持久化热水会话与订单基线轮询并补 Fake/真实 adapter contract 测试。
4. 最后清理提示文案与历史注释，运行分析、单测和真机权限验证。
5. 若权限请求或热水接口验证失败，可回滚对应 adapter/service，保留账号中心路由改动。

## Open Questions

- 用户于 2026-09-09 确认真机验证完成，权限验证任务已关闭。
- 消费订单生成意味着结束是用户确认的产品约定，真实接口缓存延迟和设备字段仍需真机验证，不声称是实时状态。
