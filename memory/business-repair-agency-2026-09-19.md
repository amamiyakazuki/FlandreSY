# 业务修复协作与决策

- 用户明确授权主代理自主决定后续业务修复分歧并告知，不再逐项等待确认；目标为现有业务缺陷修复，CI/界面优化后置。无真实设备、下单、支付或发布授权。
- 团队按阶段调用：UX Architect 梳理流程，Mobile App Builder 实现，Code Reviewer 查正确性/竞态/丢数据，Evidence Collector 独立验证；不是同时启动全部角色。UI Designer 仅界面优化阶段启用。
- 旧活动订单迁移用户选择 A：确认所属账号后才查询，确认前保留、不创建替代订单。未知历史不批量认领；旧洗衣历史的非终态记录转待确认候选，逐笔核对。
- 每业务保持全局单活动订单；异账号只能查看归属提示，切回才能操作。新订单保存 owner（当前 U净 mobile 标识；模拟隔离标识），副作用在途禁止切账号。
- 登录、重启、前台恢复只做查询，不自动重复下单/支付/启停。洗衣原有显式支付后自动启动选项保留，但只适用同账号同订单的本次成功支付，认证变化后不继续启动。
- 只读请求用认证代次隔离；由认证失效打断的在途副作用仍必须保留成功结果与原 owner。不得把“迟到响应不回写新账号”误用成丢弃已创建订单。
- 三套服务真实模式启动需凭据与账号资料，普通资料不能证明已登录；认证变更与设备资料保存互斥。旧普通身份先失效，再存新凭据，最后提交账号标识，避免中途退出身份混合。
- U净/798 HTTP 请求使用15秒总期限，迟到连接中止，不自动重发；超时不代表服务端操作一定没执行。
- BLE 有MAC优先匹配MAC，无MAC只使用明确指定的精确名称，不猜任意XN设备；缺目标信息报错。初始化失败断开，写与响应同时观察，避免早到CRC错误成为未捕获异常。
- 存储损坏按域降级、保留原件；非订单坏JSON另存恢复备份。订单域不能读时阻止新操作覆盖记录，全局告警；其它健康业务可继续。安全凭据读取失败按服务提示重登，不记录凭据原文。
- 本地自动化验证不等于真机 BLE、真实第三方接口或支付验证；最终证据以 P_PLAN/PLAN.md 与 bug.md 最新结果为准。
- 本轮最终验收：124项全量测试通过、静态分析无诊断、diff检查通过；Evidence新增21项独立验收，Code Reviewer最终无新阻断项。未执行提交、发布、CI或视觉重设计。
